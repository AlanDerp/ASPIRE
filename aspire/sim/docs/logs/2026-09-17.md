## 07:xx — DEVIATION 7 found by the coordinator: both recent Stage 2 runs were launched one `--output-dir` level too deep, so the progress reporter cannot see them

### How it surfaced

After GPU 7's Stage 2 completed at **25/50**, `gen_progress.py` still reported
`libero_goal_task (8/10 done)` with `wine_bottle → rack` marked **`stage1-done`**. A task that had
*finished* was being reported as still awaiting Stage 2 — the exact condition that invites a duplicate
dispatch, which this campaign forbids.

### Cause

`run_fix_loop_validation.py:152` builds `run_dir = output_dir / args.suite / args.task / "runs" / run_id`
— the runner appends `suite/task` itself. The default (`:71`) and the documented form
(`.claude/libero/fix-loop/main-agent-prompt.md:235`) are both `--output-dir outputs/libero_fix_loop_eval`.
Both recent runs were passed `--output-dir outputs/libero_fix_loop_eval/libero_goal_task/<task>` instead:

| | path |
|---|---|
| canonical (all eight earlier goal_task runs) | `…/libero_goal_task/<task>/runs/<run_id>/` |
| this run pair | `…/libero_goal_task/<task>/`**`libero_goal_task/<task>`**`/runs/<run_id>/` |

`gen_progress.py:242` globs `FIXED / suite / task / runs/*/manifest.json`; with the extra level it matches
nothing, so `latest_validation_manifest` returns `None`, `trials` stays `0`, and `get_status` falls through
to `stage1-done`.

**A secondary cause hid it.** `outputs/libero_fix_loop_eval/libero_goal_task` is a **symlink** into
`/mnt/nimloth/aspire_campaigns/20260917/…`, and plain `find` does not follow it — a tree-wide
`find … -name manifest.json` returned 33 manifests, all from the real-directory suites, and **silently
omitted all ten goal_task runs**. A naive manifest sweep therefore appears to confirm the layout. Use
`find -L` for any audit here.

### Impact

**The measurements are unaffected.** GPU 7's manifest is `status: complete`, 50/50 seeds,
`identity.code_sha256` matching the shipped file; all artifacts are intact and byte-correct. This is a
**layout** defect, not a measurement defect — no score in the ledger changes. What it breaks is
*discoverability*: a status file that under-reports, plus the duplicate-dispatch hazard.

### Fix (sequenced around the live run)

1. **Wait for GPU 6's `turn_on_the_stove` Stage 2 to finish** — its directory is live and must not be
   moved mid-run. (It is at 37/50 as of this note.)
2. Verify both runs' seed completeness and identity hashes.
3. Rename each tree up one level: `<task>/libero_goal_task/<task>/` → `<task>/`. Within-filesystem rename
   on the campaign mount, byte-preserving, and explicitly **not** a restart of a done task.
4. Re-verify the manifests are byte-identical and that `gen_progress.py` reports **10/10** with both run ids.

Recorded as DEVIATION 7 in the ledger with the full cause, because the failure mode it creates is one the
campaign explicitly forbids and the cause is what stops the next launcher from repeating it.

### DEVIATION 7 — resolution: a symlink, not a move (and a false alarm I nearly reported)

The plan above said "rename each tree up one level". That was **rejected on provenance grounds** before
being applied: the manifest stores each trial as an **absolute** `trial_dir` into the double-nested path,
so a move would leave **every recorded trial path dangling**. The fix used instead adds a symlink at the
canonical path and moves nothing:

```
outputs/libero_fix_loop_eval/libero_goal_task/<task>/runs -> libero_goal_task/<task>/runs
```

`pathlib` follows it, so the scanner's glob resolves; no bytes move, no hash changes, and the recorded
`trial_dir` strings still resolve (re-tested after the change — they do). Applied to GPU 7 and verified
before relying on it: **`libero_goal_task` went 8/10 → 9/10** with the row now reading
`wine_bottle → rack | done | 25/50 (50%) [run b0307177887871f6]` — correct run id, correct score.

Wart to remember: with the symlink present, `find -L … -name manifest.json` now lists that manifest
**twice** (through the symlink and through the real path). Fine for the scanner; a tree-wide audit must dedupe.

**A false alarm I nearly reported.** My first check after creating the symlink printed
`wine_bottle → rack | done | 37/50 (74%) [run 72178e81c3e4065c]`, and that run id belongs to
**`libero_goal_swap`** — which looked like the scanner reading the wrong suite. It was my own bad grep:
`grep "wine_bottle → rack" | head -1` matched the *swap* suite's row for the same task name elsewhere in
the file. Reading the goal_task section directly gave the correct `25/50 [run b0307177887871f6]`. **This
suite's task names are not unique across suites, so any grep over `fix_loop_progress.md` must be scoped to
its section** — the same two-suites-one-name hazard as the instance-count note in Promotion 0010.

Remaining: apply the same symlink to GPU 6's `turn_on_the_stove` when it finishes (its directory is live),
then confirm **10/10**.
